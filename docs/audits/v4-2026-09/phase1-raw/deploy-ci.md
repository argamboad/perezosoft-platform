### DEP-13 · High · `tools/protect-branches.ps1:22-39`, Forgejo `/branch_protections` (live), GitHub `/branches/*/protection` (live) · Neither forge protects `develop`/`main`; the protection script cannot apply here and hides its failure
**What.** PR #232 added a GitHub-only script. Live state: Forgejo `GET /repos/argamboad/perezosoft-platform/branch_protections` → `[]`; GitHub `GET …/branches/develop/protection` → `403 "Upgrade to GitHub Pro or make this repository public to enable this feature."` (`gh api …` → `{"private":true}`); GitHub `production` environment → `reviewers: []`. The script's error path is `if ($code -ne 0) { "  $branch — FAILED: …"; return }` — it prints and returns, and the process exit code stays 0, so the operator step "protect branches" can silently do nothing.
**Why it matters.** The primary forge accepts direct pushes, force pushes and deletions on the deploy branches; the `changes` gate and `qa-runlog-append-only` both *fail open* on a rewritten base (`.forgejo/workflows/ci.yml:396-406`, `:186`), so a force-push to `develop` is exactly the case the gates do not see. v3 DEP-7's "add the required reviewer" instruction is still unmet on GitHub (`docs/DEPLOYMENT.md:214-218`) — moot only while `RENDER_DEPLOY_HOOK_PROD` is absent on both forges (confirmed).
**Fix.** Add a Forgejo half to the script (`POST /repos/{o}/{r}/branch_protections` with `enable_push=false`-style rules for `develop`/`main`, status-check contexts = the gate job names), make it `exit 1` on any failure, and document that GitHub protection needs Pro or public.
**Gate.** A CI step in the `changes` job can read `/branch_protections` with the job token and fail when `develop`/`main` are unlisted (same pattern as `deploy.yml:45-79`); the script's non-zero exit is unit-testable in `tests/Api.Tests/ForgejoCiParityTests.cs` (assert the script contains `exit 1`).
**Confidence.** Certain (live state); Likely (script exit code — read, not executed).

### DEP-14 · High · `.forgejo/workflows/ci.yml:60-63` (+ every `actions/checkout@v5`), `.forgejo/workflows/deploy.yml:11-12,48` · The Forgejo job token is repo-write, is persisted into every job's `.git/config`, and the copy dropped the R63 `permissions:` floor on the strength of an unverified "cannot write" claim
**What.** The copy's rationale: "Forgejo does not support that key … Nothing in this pipeline writes with the job token … Job-token capabilities on Forgejo are granted under Authorized Integrations." `deploy.yml:11-12`: "The job token can read that API (probed 2026-09-22); it cannot write anything." Forgejo's Actions reference says the opposite model: "If the head of a pull request is from a forked repository, the secrets are not available and the automatic token only has read permissions" — i.e. for `push` and same-repo `pull_request` the token is the normal (write) one, and nothing in Forgejo 16 reads a `permissions:` key. Every job starts with `actions/checkout@v5` and its default `persist-credentials: true`, so the write token sits in the workspace for the rest of the job; on GitHub `permissions: contents: read` (`.github/workflows/ci.yml:19-20`) made that persisted token harmless — on Forgejo it is not.
**Why it matters.** Jobs execute third-party code: `dotnet workload restore` + `dotnet build` of the MAUI project, which is *outside locked-mode restore by design* (`ci.yml:264-265`), `npm ci` (pinned), Playwright `--with-deps` apt, `brew install`. With DEP-13 there is no protection to stop a `git push origin HEAD:develop` from inside a job. R63 is violated by both Forgejo files (see RULE_CONFLICTS).
**Fix.** `persist-credentials: false` on every Forgejo checkout except the one step that needs `git fetch origin` (`qa-artifacts`, `ci.yml:191`), which can receive the token in its own `env:`; pin `deploy.yml`'s "cannot write" claim with an actual probe (a `PUT` expected to 403) or delete the sentence.
**Gate.** `ForgejoCiParityTests` — assert every `uses: actions/checkout@v5` in the Forgejo copy carries `persist-credentials: false` unless allowlisted with a reason.
**Confidence.** Likely (docs + defaults; the maintainer's probe of a write is not recorded).

## Candidate rules
- **R81d-cand — [machine]** — The change classifier is safe-by-default: a path counts as code unless it matches an explicit docs allowlist (`^docs/`, `\.md$`, `README*`), and every repo path an arch test or CI gate reads (`.forgejo/**`, `.github/workflows/**`, `.github/forbidden-licenses.json`, `.dockerignore`, `docs/DEPLOYMENT.md`) is code. — Enforcement: `EnforcementGateTests.MarkdownAnywhere_IsNeverCodeOrNative` positives + a test that extracts every `Read("…")`/`File.ReadAllText(Path.Combine(root, …))` literal in `tests/Api.Tests` and asserts `Code(path)`. — Subsumes DEP-15.
- **R82d-cand — [machine]** — On a forge that ignores `permissions:`, the job token is treated as write: every `actions/checkout` sets `persist-credentials: false` unless allowlisted with a reason, no step passes `github.token` to third-party code, `develop`/`main` carry branch protection on that forge (asserted by a read of `/branch_protections` in the `changes` job), and the already-green deploy refuses a SHA with any red `native-smoke-*` task. — Enforcement: `ForgejoCiParityTests` (checkout scan, deploy.yml assertion) + a `branch-protection` step in `.forgejo/workflows/ci.yml`. — Subsumes DEP-13, DEP-14, DEP-19, DEP-27.
- **R83d-cand — [machine]** — Every container image reference — Testcontainers builders, compose, workflow `services:`/`docker run`, Dockerfile `FROM` — carries at least a `major.minor` tag or a digest; the gate scans all four surfaces on both forges. — Enforcement: `EnforcementGateTests.EveryContainerImage_IsPinned_NotFloating` widened. — Subsumes DEP-18.
- **R84d-cand — [review]** — An operator procedure in `DEPLOYMENT.md` must be executable by the scripts it names (a deploy/rollback sentence is checked against `push-to-github.sh` and the dispatch `if:` when either changes); numbers in story files (knob counts, runner capacities, token scopes) are stated once, in the runbook. — Enforcement: PR template checkbox + `ForgejoKnobs_AreTheDocumentedFour` reading the story file. — Subsumes DEP-16, DEP-25.
- **R85d-cand — [review]** — A deploy push to a mirror must not silently buy paid runner minutes: the mirror's Apple legs and scheduled smokes are behind a `vars.` knob while the mirror is a mirror, and every "repo is public/free" cost claim in a workflow comment is re-verified when visibility changes. — Enforcement: review at deploy-config PRs; the knob itself is machine-listable in the parity test. — Subsumes DEP-17.

## RULE_CONFLICTS candidates
- **R63 vs LOCALCI-4.** R63 [machine]: "every workflow declares a least-privilege top-level `permissions:`". The Forgejo copy deliberately omits it (Forgejo ignores the key and warns), `deploy.yml` omits it silently, and the parity test *asserts the omission* (`ForgejoCiParityTests.cs:109-111`). The rule's intent (least-privilege job token) is not achievable by that key on Forgejo; R82d proposes the equivalent (`persist-credentials: false` + forge-side protection). Recommend amending R63 to "…on forges that honour it; elsewhere R82d applies", not overturning it.
- **R80 text vs its test's summary.** R80 says deploys "fast-forward (never force) `develop`/`main` on GitHub"; the test's XML summary still says "deploys publish to `deploy/*` branches" (DEP-25). The rule is right; the comment is stale.

## Unknowns needing a human decision
1. **Was the Forgejo job token's *write* ability actually probed** on 2026-09-22 (a `PUT`/`POST` that 403'd), or only a read? The docs model says same-repo events get the normal token. DEP-14's severity turns on this.
2. **GitHub role going forward:** keep GitHub CI running on every deploy push (and paying macOS minutes on a private free plan, DEP-17), or make it a pure mirror (drop `develop` from its `push` trigger / knob-gate the Apple legs)? ADR-028 item 6 said "remove the hooks from GitHub"; the addendum reversed it.
3. **Branch protection strategy:** GitHub protection needs Pro or a public repo; Forgejo protection is available now and unused. Decide where protection lives, then fix `protect-branches.ps1` (fail loudly; add the Forgejo half).
4. **Maui lockfile on the desk (DEP-20):** commit per-host lockfiles and restore `--locked-mode`, or accept the floating graph on the host-mode runner and say so in ADR-028.
5. **Already-green semantics (DEP-19):** should a SHA whose *selected* smoke went red be deployable through the shortcut? The runbook's "refuses if any gate is missing, red, or skipped" suggests no.
