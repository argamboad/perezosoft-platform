# AUTH — v4 Phase 1 raw report
SHA: 8c8ed4a · BASE: f52be3d
Area: refresh-token rotation grace (#10), session keep-alive (#11), signup green list (GATES-2, #227), native api-base trailing slash (#230), auth-touching parts of #233.

## SUMMARY
Counts: Critical 0 · High 0 · Medium 1 · Low 8 · Info 4 (13 findings, AUTH-1..AUTH-13).
Headline: (1) The 60 s reuse grace is **unbounded and symmetric** — a rotated-out token can be replayed N times inside the window, each replay mints an independent live chain, and the theft alarm is also silenced when the *attacker* rotates first and the victim's own renewal lands within 60 s (which the new keep-alive timer makes predictable); ADR-002's addendum only describes the victim-first ordering. (2) Keep-alive is correctly server-authoritative and clock-injected, but nothing pins behaviour once the access token has *expired* under an unreachable server: the layout gates on `IsAuthenticated` (expiry-aware), so the shell flips to signed-out while the session is held, and a later server rejection then skips the `SignedOut` event (ADM-9 device-pref wipe). (3) GATES-2 is a genuine single choke point (all four minting paths verified) and normalizes the *input* email, but the *list* is never normalized at bind (no trim, `@`-prefixed domain, blank entry) and the invited-but-unlisted addressee founds a tenant-of-one at sign-in — a variant ADR-027 does not list under "known and accepted".
Rules proposed: R81a (one grace replay per rotated token), R82a (normalize list settings at bind), R83a (error-code parity in Postman descriptions), R84a (client session tests must cross token expiry under outage), R85a (R-rule exceptions recorded in FOUNDATION_RULES in the same PR).

## Threat questions — answers with evidence

**Q1 — Which token is returned on a grace replay?** A **NEW, independent** chain. `AuthController.cs:187` `IssueAsync` runs for both statuses; only the `Valid` branch calls `MarkRotatedAsync` (l.189–194). On `RotatedWithinGrace` nothing is written (l.196–204): the presented token keeps `RotatedAt`/`ReplacedByTokenId` pointing at the *first* successor, the first successor stays live, and the response carries a *third* token. Both chains "stay valid and rotate independently" (comment l.199–201; `RefreshReplayTests.cs:84–109` asserts `rotated1 != rotated2` and both refresh OK).
**Is the grace keyed atomically to the rotation link?** The read is keyed to the link (`RefreshTokenService.cs:141–152`: `RotatedAt`, `ReplacedByTokenId`, successor `!IsRevoked && ExpiresAt > now`, `successor.UserId == token.UserId`) but the decision and the issue are **not** in one transaction — see AUTH-2. **Is it bounded?** No counter, no stamp on the grace path: any number of replays inside 60 s each mint a chain (AUTH-1). **After the grace?** `Reuse` → `RevokeAllUserTokensAsync` (l.171–177); pinned by `RefreshReplayTests.cs:34–64` (ages `RotatedAt` by 61 s) and `TokenServiceTests` (61 s → Reuse, successor revoked/expired → Reuse, grace 0 → Reuse, revoked-never-rotated → Reuse; boundary at exactly 60 s is inclusive, l.218). Logout/revoke-all/staff MFA reset all go through `RevokeAllForUserAsync` (set-based, never stamps `RotatedAt`; `RefreshTokenRepository.cs:63–66`, `AdminController.cs:358`), so the "live successor" condition does keep a sign-out final (`RefreshReplayTests.cs:112–133`). **Can an attacker keep a session alive by racing every rotation?** They do not need to: one in-window replay (attacker-first *or* victim-first ordering) yields an independent chain that then rotates normally for up to `ExpiryDays` sliding — undetectable until the victim logs out (AUTH-1).

**Q2 — Keep-alive.** Triggers: timer armed in `AcceptTokensAsync` (`AuthService.cs:650`), bearer handlers via `GetFreshAccessTokenAsync` (l.698–706; `AuthHeaderHandler.cs:13`, `NativeAuthHeaderHandler.cs:17`), native window `Resumed`/`Activated` → `AppResumeNotifier` → `MainLayout.OnResumed` (`App.xaml.cs:24–25`). Signed-out/impersonating: `GetFreshAccessTokenAsync` returns early on `!_sessionHeld || IsImpersonating` (l.700); `RenewInBackgroundAsync` same guard (l.753); `BeginImpersonation` cancels the timer (l.599); `ClearSessionAsync` cancels it (l.660). No renew loop while signed out — pinned (`SessionKeepAliveTests` `AfterLogout_NothingRenews`, `WhileImpersonating_…`, `ARequest_NeverSignedIn_…`). Network errors → `Unreachable` (keep everything, retry in 30 s; l.208–214, 228–232, 760–762) — neither infinite-session (server stays authoritative; a 401/400/403 clears) nor silent sign-out **as long as the access token is still unexpired** — see AUTH-5 for what happens past expiry. Clock: `TimeProvider` injected (l.46, 114) and timers via `Time.CreateTimer` (l.736); tests run on `FakeTimeProvider`. Renewal never sooner than 30 s (l.728–729) — a fast device clock cannot tight-loop.

**Q3 — Signup gate.** Single choke point confirmed: the only `new User` sites in `src/` are `UserService.cs:118` (OAuth path, `GetOrCreateUserAsync`) and `:156` (`GetOrCreateByEmailAsync`), both funnelling into `CreateUserWithTenantAsync` (l.174–180) where the gate fires before any write; `AuthController.cs:111` and `NativeAuthController.cs:91` (web/native OAuth) call `GetOrCreateUserAsync`; `PasswordlessService.cs:83,122` (magic link, OTP) call `GetOrCreateByEmailAsync`; `UserRepository.cs:41` is the only `Users.Add`, reached only via those. E2E signs in via OTP (`E2ETestBase.cs:88`) — the gated path; `IntegrationTestFactory.SeedUserAsync` and `SignupGateTests` seed via `DbContext` directly (test-only bypass, acceptable). Normalization: both callers `Trim().ToLowerInvariant()` the email before the gate (`UserService.cs:79, 145`); `SignupSettings.Allows` is `OrdinalIgnoreCase` (l.34, 38) and the invitation lookup lower-cases (`TenantInvitationRepository.cs:45`), `InvitedEmail` is stored normalized (`TenantInvitationService.cs:79`). The **list** side is not normalized (AUTH-7). Owner check: done at **account-creation** time (`SignupGate.cs:47–56` → `GetMemberDetailsAsync`, role `owner`); acceptance itself is not gated (ADR-027 §4: creation only) — so an ownership transfer between invite and accept is irrelevant to admission, and a transfer *before* sign-in is honoured (the current owner is read live). `TenantMembership` is not `ITenantScoped` (`TenantMembership.cs:10`) so the pre-auth owner read is not filtered; `TenantInvitation` is scoped and the read uses the `IgnoreQueryFilters().TagWith(RlsTags.CrossTenant)` hatch inside Infrastructure (allowed; the Features ban does not apply). ## Findings

### AUTH-1 · Medium · `src/Api/Services/RefreshTokenService.cs:124–153`, `src/Api/Controllers/AuthController.cs:187–204`
**What.** The reuse grace is (a) unbounded — no per-token "grace used" stamp, so the same rotated-out token can be replayed any number of times inside 60 s and each replay mints a fresh, independent, fully-rotatable chain; (b) symmetric — the alarm is silenced not only when a thief replays *after* the victim, but when the thief rotates *first* and the victim's own renewal lands within 60 s (the `Valid`→`MarkRotated` path stamps `RotatedAt` for the thief's rotation exactly like a legitimate one, so the victim is the one classified `RotatedWithinGrace`); (c) schedulable — the #11 timer renews one minute before `exp` on a fixed cadence, so a holder of the cookie/secure-store token can present it just before the victim's predictable renewal. `/api/auth/refresh` carries no `[EnableRateLimiting]` (only the passwordless endpoints do, l.263/316/338), so (a) is also a cheap row-minting amplifier.
**Why it matters.** R51's rotation/reuse family revocation (v3 TB-AUTH-1) was the only theft signal for refresh tokens. Under (b) the thief's chain survives undetected until the victim explicitly logs out — and #11 is precisely about users *not* logging out. ADR-002's 2026-09-18 addendum states only the victim-first trade ("a thief who replays a stolen token within 60 s of the victim's rotation").
**Evidence.**
```
// RefreshTokenService.cs:124-129 — status only; nothing is written for the grace outcome
if (token.IsRevoked) { var status = await IsRotatedWithinGraceAsync(token, ct) ? RotatedWithinGrace : Reuse; return new(status, token); }
// AuthController.cs:187, 196-204 — a NEW chain, the presented token untouched
var session = await sessionService.IssueAsync(user, presented.Provider, ClientIp, native, ct);
... else { logger.LogInformation("Refresh token presented again within the rotation grace window ..."); }
```
`RefreshReplayTests.cs:84–109` pins two presentations; nothing pins a third, and nothing pins the attacker-first ordering.
**Fix (one line).** Make the grace one-shot per rotated token: on the grace path link the *presented* token's chain to the new issue (or stamp `GraceUsedAt`) so a further presentation is `Reuse`; log grace at Warning with the count; amend the addendum to state the attacker-first case; consider a per-IP limiter on `/refresh`.
**Gate.** `tests/Api.Tests/Integration/RefreshReplayTests.cs` (third presentation inside the window → 401 + revoke-all) and `tests/Api.Tests/TokenServiceTests.cs` (grace-used token → Reuse). Machine-catchable once the rule exists.
**Confidence.** Certain for the code behaviour; Likely for exploitability (needs a stolen refresh token — cookie is HttpOnly, native store is OS-protected — the same precondition R51 already assumes).

### AUTH-2 · Low · `src/Api/Controllers/AuthController.cs:170–194`
**What.** Inspect → `GetUserByIdAsync` → `IssueAsync` (INSERT) → `MarkRotatedAsync` are four separate round-trips with no transaction or fence. A `RevokeAllForUserAsync` (logout, reuse response, staff MFA reset) that commits between the inspection and the INSERT leaves the newly inserted token live after the revoke-all. The `Valid` path had this window before the delta; the grace path adds a second class of *already-revoked* tokens that can mint through it.
**Evidence.** `IsRotatedWithinGraceAsync` reads the successor once (`RefreshTokenService.cs:148`); `RevokeAllForUserAsync` is `ExecuteUpdate … WHERE !IsRevoked` (`RefreshTokenRepository.cs:63–66`) and cannot see a row inserted after it ran. `RefreshReplayTests.cs:112–133` is sequential (logout completes before the stale replay).
**Fix.** Issue and mark inside one transaction and re-check the fence at commit (e.g. conditional `UPDATE successor SET … WHERE IsRevoked=false` affected==1 for the grace path; for `Valid`, `MarkRotated` as a conditional `WHERE IsRevoked=false`, roll back the insert on 0 rows).
**Gate.** Not cheaply machine-catchable (needs interleaving); document as a review item in the harness notes. **Confidence.** Suspected (runtime interleaving not executed here).

### AUTH-5 · Low · `src/Shared.Ui/Auth/AuthService.cs:656–668`, `src/Shared.Ui/Layout/MainLayout.razor:27`
**What.** Past the access token's `exp` under an unreachable server the session is *held* (`_sessionHeld` true, retry timer live) but `IsAuthenticated` (expiry-aware, l.116) is false: (a) the layout's render gate `else if (!Auth.IsAuthenticated)` (MainLayout l.27) flips the shell to the anonymous branch — the "silent sign-out" symptom the brief asks about, at the UI layer, until the next successful renewal raises `SignedIn`; (b) if the server then answers 401 (token revoked meanwhile), `ClearSessionAsync` computes `wasAuthenticated = IsAuthenticated` = false and **does not raise `SignedOut`**, so `MainLayout.OnSignedOut`'s device-preference wipe (v3 ADM-9) is skipped.
**Evidence.**
```
// AuthService.cs:656-668
var wasAuthenticated = IsAuthenticated;   // false once exp has passed
... if (wasAuthenticated) SignedOut?.Invoke();
```
`SessionKeepAliveTests.MidSession_ServerError_KeepsTheSession_AndTriesAgainShortly` asserts only "the current token still has a minute to live"; no test advances past `exp` while unreachable, then rejects.
**Fix.** Gate the layout on a session-held notion (`HasSession => _sessionHeld`) and derive `wasAuthenticated` from `_sessionHeld` rather than token expiry.
**Gate.** `tests/Ui.Tests/SessionKeepAliveTests.cs` — add "unreachable through expiry, then 401 → `SignedOut` raised exactly once; then renewed → body re-rendered without a `/login` bounce". **Confidence.** Suspected for (a) (render path not executed), Certain for (b) (code-evident).

### AUTH-7 · Low · `src/Api/Configuration/SignupSettings.cs:31–39`, `src/Api/Program.cs:45–46`
**What.** The green list is bound raw: no `Trim`, no drop of blank entries, no tolerance for a leading `@` on a domain. `Signup__AllowedEmails__0=" Friend@x.com"` or `Signup__AllowedDomains__0="@x.com"` silently admits nobody; uncommenting `.env.example`'s `#Signup__AllowedEmails__0=` with no value may bind `[""]` → `IsRestricted` true with an empty effective list (a locked deployment). `Allows()` itself does not trim its input (callers do today).
**Why.** Fails closed (refuses), so not a leak — but the platform's normalization discipline (fail-closed normalization, R-rules on email handling) is applied to the *input* and not to the *policy*, and the only signal is the startup posture line.
**Evidence.** `if (AllowedEmails.Contains(email, StringComparer.OrdinalIgnoreCase)) return true;` — no normalization of the array; `SignupGateTests` covers case only (`ListOf("Friend@Example.com")`).
**Fix.** Normalize after `Bind` (trim, lower, strip leading `@`, drop blanks) in one place. **Gate.** `tests/Api.Tests/Auth/SignupGateTests.cs` theory over `" x@y "`, `"@y"`, `""`; `ConfigPostureTests`. **Confidence.** Certain (blank-entry binding: Suspected).

### AUTH-8 · Low · `src/Api/Services/UserService.cs:174–215`, `docs/DECISIONS.md` ADR-027 "Known and accepted"
**What.** Admission via invitation happens at *account creation*, which unconditionally founds a tenant-of-one (Tenant + owner membership, l.186–213). An invited-but-unlisted addressee therefore owns a household from the moment they sign in; if they never accept, if the invitation is revoked/expires before they accept, or if they add data first (`AcceptAsync` → `WouldAbandonData`, `TenantInvitationService.cs:204–206`), they keep a household founded outside the list. ADR-027 accepts only the `ReHomeAsync` variant ("someone who leaves").
**Why.** Contradicts the story's one-line rule ("the green list decides who may FOUND a household") in letter; in practice the same "admits nobody new" argument applies, so it is cosmetic — but undocumented.
**Fix.** Extend ADR-027's accepted-consequence paragraph (and `gates.md` l.41) to the sign-in-time tenant-of-one; or, if not acceptable, defer household creation for gate-by-invitation sign-ins (larger change; multi-household ADR l.1579 already anticipates a second front door).
**Gate.** Doc-only; no test. **Confidence.** Certain.

### AUTH-9 · Low · `docs/postman/Perezosoft.postman_collection.json` (OTP verify l.~100; magic-link verify; OAuth callbacks)

### AUTH-12 · Low · `src/Api/Controllers/AuthController.cs:111–114 vs 133–138`, `NativeAuthController.cs:91, 102–105`

### AUTH-4 · Low · `src/Shared.Ui/Auth/AuthService.cs:650, 724–738`; `src/Api/Services/RefreshTokenService.cs:93`

## Candidate rules
