Builds on Phase 1 (AUTH-1..13, UX-6..18 adjudicated — not re-filed), Phase 2 (909/909 green; `SessionKeepAliveTests` 14, `RefreshReplayTests` 4), v3 LOGIC_AND_TEST_REPORT Part A (LB-AUTH-1..3, LB-UI-1..10 adjudicated).

## SUMMARY
- **Part A — 10 new wrong-RESULT findings: 5 Certain · 4 Likely · 1 Suspected** (server LB-AUTH-4..7, client LB-UI-11..16). Severity: 1 High (LB-AUTH-5) · 5 Medium · 4 Low.
- **Headline (3 lines):** (1) **Logout is not final under the keep-alive** — `POST /api/auth/logout` resolves its user with `ValidateRefreshTokenAsync` (live tokens only), so a logout that presents a token the timer just rotated out revokes NOTHING and answers 200; the client then re-accepts the in-flight refresh and the user is signed in again (LB-AUTH-4 + LB-UI-12). (2) **The accept path dissolves the joiner's empty tenant-of-one with `DeleteTenantAsync`, not `ITenantDissolutionService`** — the three plumbing contributors never wipe, orphaning API keys (which still authenticate to the dead tenant), webhook subscriptions/deliveries and usage counters — v3 LB-TEN-1's hole reopened through a third dissolve flow the registration canary cannot see (LB-AUTH-5). (3) **`AuthService` has no session epoch and reads impersonation from an expiry-gated claim** — a refresh in flight across `BeginImpersonation`/`LogoutAsync` overwrites the new state, and an expired impersonation token is silently renewed into the STAFF identity mid-page by the bearer handler (LB-UI-11/12/13); plus the client trusts the device clock against a server with `ClockSkew = Zero` (LB-UI-14).
- **The green suite cannot see any of these**: every one is an interleaving (refresh × logout/impersonation/accept), a call-site bypass, a clock-offset, or a boundary — there is no epoch test, no skew test, no "dissolve through accept" test, no logout-with-stale-token test.
- **Part B — 30 specs** (TB-AUTH-13..30, TB-UI-17..28) incl. the nine Phase 1 asked for and six tenancy negatives. **Harness:** server ready for 11/18 as-is (3 need a one-line `ServiceHarness` overload, 1 needs a factory clock, 2 blocked on the v3-noted fault injector); client ready for 8/12 (4 need a clock-offset seam in `ComponentTestBase`/`TestJwt`).
- **Rules proposed:** R123a–R127a. **Conflicts logged:** 3.

## Part A findings

### LB-AUTH-5 · **Certain** · High · `src/Api/Services/TenantInvitationService.cs:249-250` (vs `TenantService.cs:211`, `AccountErasureService.cs:74`)
**Intended:** DEBT-7/ADR-011 — every tenant dissolve runs the shared sequence (`ITenantDissolutionService.DissolveAsync`: each `ITenantDataContributor.WipeAsync`, then `WipeDataAsync`) so per-tenant erasure is complete (R12/R13/R43 spirit). **Actual:** `AcceptAsync` dissolves the joiner's empty tenant-of-one with
```
249  if (dissolveOld)
250      await tenants.DeleteTenantAsync(oldTenantId, cancellationToken);
```
— a raw `Tenants.Remove` (`TenantRepository.cs:101-106`). FK cascade covers memberships/invitations only (ADR-003: tenant-scoped entities carry a plain Guid, no FK). The `dissolveOld` guard is `!TenantHasDataAsync`, but `ApiKeyDataContributor`, `WebhookDataContributor` and `UsageCounterDataContributor` return `HasDataAsync == false` BY DESIGN ("operational plumbing, must not block") — so a solo owner with API keys / webhook subscriptions / usage rows passes the guard and the rows are orphaned. **Trigger:** owner of a tenant-of-one creates a PUBAPI key or a HOOKS subscription (or any metered call writes a `UsageCounter`), then accepts an invitation. **Wrong output:** rows for a non-existent tenant survive; `ApiKeyService.AuthenticateAsync:89` looks the key up by hash with `QueryAllTenants()` and never checks the tenant exists → the key still mints an `ApiKeyAuthResult(TenantId = dead)` and public-API writes stamp rows into the dead tenant. **Correct:** the accept-path dissolve is the same sequence as leave/erasure. **Fix (one line):** inject `ITenantDissolutionService` and replace line 250 with `await dissolution.DissolveAsync(oldTenantId, cancellationToken)` (it already `EnterTenant`s the target — RLS-2 — and enlists in the ambient transaction). **Why the canary missed it:** `ArchitectureTests.EveryTenantOwnedEntity_IsWiredIntoTenantDissolution:109` proves every entity has a contributor; nothing proves every dissolve *call site* uses the service. **Test that would have caught it:** new `tests/Api.Tests/Tenancy/AcceptDissolveTests.cs` `Accept_DissolvingAnEmptyTenantOfOne_WipesPlumbingRows` (TB-AUTH-20) + arch gate TB-AUTH-21.

### LB-AUTH-4 · **Certain** · Medium · `src/Api/Controllers/AuthController.cs:236-241` + `RefreshTokenRepository.cs:21-28`
**Intended (docstring l.220-223, ADR-002 addendum):** "Revokes all refresh tokens for the session … Idempotent"; "logout and revoke-all revoke the successor, so a stale token can never undo a sign-out". **Actual:** the user is resolved with `ValidateRefreshTokenAsync` → `GetValidTokenByHashAsync` (`!IsRevoked && ExpiresAt > now`). A presented token that was **just rotated out** (grace window), or that expired, is `null` → no `RevokeAllUserTokensAsync`, cookie deleted, **200 "Logged out successfully"**. **Trigger (per hour, both hosts, made routine by #11):** the keep-alive refresh is in flight when the user clicks Sign out — web: the cookie jar still holds T0 until the refresh's `Set-Cookie` lands; native: `sessionStore` still holds T0 until `AcceptTokensAsync` saves S1. Logout presents T0 → server: T0 is `IsRevoked` (rotated) → no-op. Then the refresh response arrives: web — its `Set-Cookie` re-creates the refresh cookie AFTER the logout's delete; native — the client stores S1. **Wrong output:** S1 stays live server-side; the next launch (or LB-UI-12 immediately) restores the session the user just ended. A second, non-racy variant: a token expired between the last renewal and the click (device asleep) → logout revokes nothing for the user's other devices although the docstring says "all". **Fix (one line):** resolve the user through `InspectRefreshTokenAsync` and revoke the family for `inspection.Token?.UserId` whenever `Token is not null` (Valid, Expired, Reuse and RotatedWithinGrace all name their owner; only Unknown does not). **Test:** `tests/Api.Tests/Integration/RefreshReplayTests.cs` `Logout_WithTheTokenJustRotatedOut_StillRevokesTheSuccessor` (TB-AUTH-18) — fails today.

### LB-AUTH-7 · **Likely** · Low · `src/Api/Services/QuotaService.cs:31-32` via `TenantInvitationRepository.GetPendingForTenantAsync:25-29` (seat re-check `TenantInvitationService.cs:222`)
**Intended (BILLING-5/9):** "seats = members + still-pending invites (a pending invite is a reserved seat)". **Actual:** `GetPendingForTenantAsync` filters `Status == Pending` only — no `ExpiresAt` predicate — and nothing flips an expired invitation to a terminal status. An invitation nobody accepted keeps its seat **forever** after its 7-day `LifespanDays`. **Trigger:** Free tenant (cap 5) with 3 members + 2 invites that expired weeks ago → `CanAddSeatsAsync(1)` = false → the owner cannot invite anyone (`SeatLimitReached`) and — the accept-side re-check — a *valid* invitee gets `402 seat_limit_reached` at `AcceptAsync:222-223` because `CanAdd(0)` counts the two dead invites. **Correct:** an invitation past `ExpiresAt` reserves nothing (it is `InvalidToken` for everyone at `AcceptAsync:183`, and `GetValidByEmailAcrossTenantsAsync` already excludes it for the gate). **Fix:** add `&& i.ExpiresAt > now` to the seat count (or an expiry sweep). **Test:** `tests/Api.Tests/Billing/AcceptSeatQuotaTests.cs` `ExpiredPendingInvites_DoNotReserveSeats` (TB-AUTH-23). Not found in v2/v3 reports (grep: no hit) — new.

### LB-AUTH-6 · **Certain** · Low · `src/Infrastructure/Repositories/TenantInvitationRepository.cs:52` vs `src/Api/Services/TenantInvitationService.cs:181-184`
Boundary inconsistency: the signup gate's lookup treats `ExpiresAt >= now` as valid; the accept treats `ExpiresAt <= now` as invalid. At `now == ExpiresAt` the gate admits the addressee (they found a tenant-of-one, AUTH-8) and the accept refuses the same invitation one call later. Also `GetPendingForTenantAsync` (seat count) and `GetPendingByEmailAsync` (refresh-not-duplicate) apply no expiry predicate at all — three different validity predicates for one entity. **Fix:** one `TenantInvitation.IsValidAt(now)` (`Status == Pending && ExpiresAt > now`) used everywhere. **Test:** `SignupGateTests.InvitationExpiringNow_IsInvalidForBothGateAndAccept` (TB-AUTH-22).

### LB-UI-13 · **Certain** · Medium · `src/Shared.Ui/Auth/AuthService.cs:588,697-706,803-805` + both bearer handlers
**Intended (ADR-014, ADR-002 addendum "Unchanged: impersonation tokens are never renewed"):** an impersonation token is short-lived (15 min, `AdminController.cs:39`) and non-refreshable; "a reload or expiry returns the staff user to their own identity". **Actual:** `IsImpersonating => Claim(ImpersonatedBy) is not null` and `Claim()` returns null once the token is expired (l.805). At minute 15 the guard in `GetFreshAccessTokenAsync` (l.700) no longer sees impersonation → `RenewalDue ≤ 0` → `RefreshAsync()` → the **staff** token is accepted silently. Pre-delta the next request 401'd (visible); post-#11 the bearer handler renews before sending, so **the request the admin issues from the target's page is executed as the staff user in the staff's own tenant** (e.g. a note create on the target's Household page lands in the admin's household). `AcceptTokensAsync` raises `SignedIn` (wasAuthenticated false → true) — so the admin's device prefs are reconciled from the staff token — but never `IdentityChanged`, so the header keeps showing the target until the next render. **Fix:** track impersonation in a field set by `BeginImpersonation` and cleared only by `StopImpersonationAsync`/`ClearSessionAsync`; on expiry raise `IdentityChanged` (or navigate to `/`) instead of renewing. **Test:** `SessionKeepAliveTests.ImpersonationExpiry_DoesNotSilentlyRenewIntoTheStaffIdentity` (TB-UI-24). `AuthServiceTests.Impersonation_IsClaimDriven_…` pins the claim-driven reading that causes this.

### LB-UI-11 · **Likely** · Medium · `src/Shared.Ui/Auth/AuthService.cs:595-603,641-654`
**Intended:** `BeginImpersonation` cancels the renewal "so the staff session's renewal must not fire under the impersonation". **Actual:** `CancelRenewal` disposes the timer but cannot cancel a `RunRefreshAsync` already awaiting `PostAsync`; `AcceptTokensAsync` has no guard — it overwrites `_accessToken` with the staff token, re-arms the timer, and raises nothing (`wasAuthenticated` true). **Interleaving:** the timer fires (exp − 60 s) during the `POST /api/admin/impersonate/{id}` round-trip (the impersonate request itself went out on the pre-renewal token because `RenewalDue` was still > 0 by milliseconds). **Wrong output:** the "sign in as" ends the instant it starts; `IsImpersonating` false, banner gone, but no `IdentityChanged` → header stale; the admin's next actions run as themselves. **Fix:** a session epoch (`int _epoch`, incremented in `ClearSessionAsync`/`BeginImpersonation`; `RunRefreshAsync` captures it and `AcceptTokensAsync` discards a payload from an older epoch). **Test:** `SessionKeepAliveTests.ARefreshInFlight_WhenImpersonationBegins_IsDiscarded` (TB-UI-22) using `Http.OnGated`.

### LB-UI-12 · **Likely** · Medium · `src/Shared.Ui/Auth/AuthService.cs:618-638,641-654,656-668` (client half of LB-AUTH-4)
`LogoutAsync` → `ClearSessionAsync` (token null, `_sessionHeld=false`, timer cancelled, `SignedOut` raised → MainLayout wipes device prefs, ADM-9). A refresh in flight then completes with 200 → `AcceptTokensAsync`: `_sessionHeld=true`, token set, timer armed, **`SignedIn` raised** (wasAuthenticated false) → `ReconcilePreferencesAsync` re-adopts/re-writes the prefs just wiped; native: `SaveRefreshTokenAsync(S1)` re-populates the store the logout cleared. **Wrong output:** after "Logged out", the app is signed in (a valid 60-min JWT in memory regardless of what the server revoked; with LB-AUTH-4 the chain is live too). `AuthFlowTests.SignOut_ReturnsToLogin` cannot see it (no in-flight refresh). **Fix:** same epoch as LB-UI-11. **Test:** `SessionKeepAliveTests.ARefreshInFlight_WhenLoggingOut_DoesNotResurrectTheSession` (TB-UI-23).

### LB-UI-14 · **Certain** (mechanism) / Likely (exposure) · Medium · `src/Shared.Ui/Auth/AuthService.cs:709-722,818-829` vs `src/Api/Configuration/JwtValidation.cs:23-24` (`ClockSkew = TimeSpan.Zero`)
The client derives every deadline from the JWT `exp` on the **device** clock; the server tolerates zero skew; the API already returns `expires_in` (`SessionService.cs:54`) which the client ignores. (a) **Device slow by S > 60 s:** the timer fires at real `exp + (S − 60 s)`; between real `exp` and that instant `GetFreshAccessTokenAsync` returns the token as fresh (`RenewalDue > 0`), the server 401s, and **neither bearer handler reacts to a 401** (no refresh-and-retry) → every page call fails for `S − 60 s` each hour, shown as errors/empty lists; the addendum's "a request renews it first if the timer was missed" is false for this class. (b) **Device fast by F ≥ token lifetime (60 min):** every accepted token reads as expired → `IsAuthenticated` false, `SignedIn` never fires, the layout stays on the anonymous branch, and `ScheduleRenewal` floors to 30 s → a **30 s rotation loop** (2 880 rotations/day, each a live-successor chain) with the user seeing "signed out". Pre-delta (b) was one refresh then `/login`; the loop is new. **Fix:** compute the renewal deadline as `receivedAt(Time) + expires_in − lead` (server-relative, monotonic on the client), and add one-shot refresh-and-retry on 401 to both handlers (they already own `GetFreshAccessTokenAsync`). **Tests:** `SessionKeepAliveTests` skew theory (TB-UI-25/26) — needs the clock-offset seam (Harness readiness).

### LB-UI-15 · **Likely** · Low · `src/Shared.Ui/Auth/AuthService.cs:714-715` vs `src/Api/Services/JwtTokenService.cs:69-74`
"Capped at a quarter of the token's lifetime" is computed from `jwt.ValidFrom` (`nbf`). The server issues `expires:` only — no `notBefore`, no `iat` (grep: none) — so `ValidFrom == DateTime.MinValue`, `lifetime := RenewLead * 4`, lead is always 60 s; the cap branch executes only for `TestJwt` tokens (which set `notBefore`). A deployment with `Jwt:ExpiryMinutes ≤ 2` renews on arrival → floored to the 30 s loop of LB-UI-14(b). **Fix:** same as LB-UI-14 (`expires_in`), or emit `iat`. **Test:** `RenewalDue_ForAServerShapedToken_WithoutNbf_CapsTheLead` (TB-UI-27) building the token without `notBefore`. Runtime not executed → Likely (JwtPayload adds `nbf` only when `notBefore` is supplied).

### LB-UI-16 · **Suspected** · Low · `src/Shared.Ui/Pages/Join.razor:112-117` + `AuthService.cs:158-176`
Join calls `Auth.TryRefreshAsync()` after a 204 accept "so the new household shows". `RefreshAsync` coalesces onto `_refreshInFlight` — a timer renewal that started **before** the accept committed returns a token whose `tenant_id`/`tenant_name` were resolved against the OLD membership (`SessionService.ResolveTenantAsync` ran before the move). **Interleaving:** timer fires during the accept round-trip; the server's `ResolveTenantAsync` read precedes the accept's commit. **Wrong output:** `_state = Success` with a JWT scoped to the dissolved tenant-of-one for up to an hour — every tenant-scoped call returns nothing (RLS + filter) and writes stamp into a deleted tenant. **Fix:** `TryRefreshAsync(force: true)` that awaits the in-flight task then issues its own; or an epoch-aware "refresh after X" API. **Test:** bUnit `Join` with a gated refresh started by the timer before the accept response (TB-UI-28).

**Verified NOT bugs (asked by the task):** `SignupGate.Allows` under an unset `ICurrentTenant` — `TenantMembership`/`User` are not `ITenantScoped` (no global filter, not RLS'd), the invitation read is tagged cross-tenant, pre-auth `RlsTenantId` null ⇒ bypass GUC: a legitimately invited user is admitted (TB-AUTH-24 pins it). `TryAcceptAsync` vs the seat read at the cap — the accept is seat-neutral (joiner consumes the seat its invite reserved), so two invitees accepting concurrently at the cap end at exactly the cap; not a TOCTOU. `WouldAbandonData` — contributors use `QueryAllTenants()` + explicit `TenantId`, independent of the entered tenant. `IssueAsync`→`MarkRotatedAsync` order — a crash between them leaves T0 Valid and S1 unused: the retry rotates normally (safe, non-idempotent by design); lost response after both → grace chain (as designed). `ReuseGraceSeconds ≤ 0` → strict. Legacy revoked row with null `ReplacedByTokenId` → `Reuse` (correct). `>` at l.145 makes exactly 60 s inclusive (documented, pinned). `_refreshInFlight` is never cancelled by a request's `CancellationToken` (handlers don't pass one) — no shared-cancel bug. `StopImpersonationAsync` re-arm: `TryRefreshAsync` → Renewed re-arms via `AcceptTokensAsync`; Unreachable leaves no timer but the `forceLoad` reload re-initialises — acceptable; Rejected skips `SignedOut` (`_accessToken` already null) — same class as AUTH-5(b), not re-filed.
