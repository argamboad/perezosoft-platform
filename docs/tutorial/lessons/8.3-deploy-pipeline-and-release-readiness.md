# Lesson 8.3 — The deploy pipeline & release readiness

> **Part 8 · Ship it.** The DevOps thread that started in lesson 1.6 — a CI workflow born at the
> first commit and grown a job per part — reaches its destination here: it learns to *deploy*.
> A deploy is a button: a person runs the workflow with `deploy` = staging (or prod), the run
> re-runs every gate, and only then deploys — and then **proves the new build is actually live**
> before calling it green. §5 explains why nothing deploys on a merge, and why the expensive native
> legs run only when asked for, once every Actions minute is billed (ADR-031). But automation is only half of release
> readiness. The other half is a **QA test plan**
> — a maintained, human-run checklist across web and the native shells — because some regressions
> (a broken OAuth redirect on a real device, a visual glitch) no automated gate will ever catch.
> The lesson's thesis: *automation gates regressions; the QA pass gates releases.*

**Goal:** a CI pipeline where a deploy is a deliberate dispatch that re-runs every gate first, then a
version-gated post-deploy smoke waits for *this commit* to be live before asserting; staging deploys
from `develop`, prod from `main`, and a wrong branch fails loudly; concurrent deploys don't spuriously
fail each other; pull requests run the web gates only, and the native legs run on request; and a QA
test plan exists as a maintained artifact that
gates releases the automation can't.

**Concepts & principles:** continuous delivery (deploys on demand, each behind every gate); the
version-gated smoke (why health alone can't tell old build from new); post-deploy assertions;
deploy concurrency (cancel-in-progress); deploy as a human dispatch with a branch guard; a run plan
that decides once what a run is for; billed minutes as a design input (web gates per PR, device legs
on request); regressions-vs-releases (what automation gates vs what a human QA pass gates); the QA
plan as a versioned artifact.

**Maps to:** ADR-017, DEPLOY-3, ADR-031 (ADR-028 → ADR-030 for the Forgejo era) · repo:
`.github/workflows/ci.yml` (the `changes` run plan, the `deploy-staging` / `deploy-prod` jobs),
`.github/scripts/deploy-smoke.sh`, `src/Api/Program.cs` (`/api/version`),
`tests/Api.Tests/CiWorkflowTests.cs`, `tests/ci-logic/` (the run plan's fixtures), `docs/QA_TEST_PLAN.md`.

**Prerequisites:** 1.6 (the CI workflow this extends), 8.1/8.2 (single-origin + the container +
`render.yaml` being deployed), 4.5 (`/health` liveness/readiness — two of the smoke's probes; the
third, `/api/version`, is built in this lesson).

---

## 1. Motivate — "deployed" is not "live", and green tests aren't a release

Two subtle truths shape this lesson. First: triggering a deploy is not the same as the new build
serving traffic. On a rolling host the *old* instance keeps answering while the new one builds and
boots — so if your pipeline triggers a deploy and immediately curls `/health`, it gets a cheerful
200 *from the old build* and reports success before your change is even live. A deploy pipeline
that can't tell "old build still up" from "new build live" is lying to you. Second: a full green CI
run means your *code* is correct against your *tests* — it does not mean the *release* is good. Does
Google sign-in actually complete on a physical Android device? Does the invite email render in a
real inbox? Does the desktop shell's window restore correctly? Automated tests can't economically
cover all of that, and pretending they do is how a "green" release ships a broken OAuth flow. So
the pipeline gets a *version-gated* smoke that proves liveness of the right build, and release
readiness gets a *human* QA pass for what automation can't reach.

## 2. Deploy to staging — a button, behind every gate

```yaml
# .github/workflows/ci.yml — deploy-staging
deploy-staging:
  needs: [build-test, secret-scan, qa-artifacts, license-scan, docker-build, e2e]   # only after all gates green
  if: github.event_name == 'workflow_dispatch' && inputs.deploy == 'staging'
  concurrency: { group: deploy-staging, cancel-in-progress: true }
  steps:
    - name: Staging deploys from develop        # a wrong branch fails loudly
      run: '[ "${{ github.ref }}" = refs/heads/develop ] || { echo "::error::staging deploys from develop"; exit 1; }'
    - name: Trigger Render deploy
      run: curl -fsS -X POST "$RENDER_DEPLOY_HOOK_STAGING" > /dev/null
```

The shape: nothing deploys on a push or a merge. A person opens Actions → CI → *Run workflow*, picks
`deploy` = staging on `develop`, and that run re-runs the **full quality bar** — the `needs:` list gates
the deploy behind build/test, secret-scan, license-scan, the E2E suite, and the docker image build. A
deploy is downstream of proof, and of a decision. The first step refuses any branch but `develop`, so a
dispatch from the wrong place fails red instead of deploying it. The `concurrency` block with
`cancel-in-progress: true` handles two deploy runs close together: the older deploy job is *cancelled*
rather than left to race — because (§3) the older run's version-gated smoke could never see its own
commit go live once a newer build superseded it, and would fail spuriously. Cancelling reads as neutral;
the newest run still runs its full smoke. Concurrency control here is a correctness fix, not tidiness.

## 3. The version-gated smoke — prove the *new* build is live

This is the clever, load-bearing part. After triggering the deploy, the pipeline **polls
`/api/version` until it reports *this workflow's commit SHA*** and readiness is 200 — only then does
it run assertions:

```yaml
# wait for the NEW build to actually be live (the old instance serves during the build)
EXPECT=${{ github.sha }}
for i in $(seq 1 50); do
  got=$(curl -s "$BASE/api/version" | jq -r '.commit')
  code=$(curl -s -o /dev/null -w '%{http_code}' "$BASE/health/ready")
  if [ "$got" = "$EXPECT" ] && [ "$code" = "200" ]; then ready=1; break; fi
  sleep 15                                   # free-tier build + cold boot can take minutes
done
[ "$ready" = 1 ] || { echo "::error::new build did not go live in time"; exit 1; }
```

`/api/version` is a small endpoint you add *in this lesson* (DEPLOY-3) — anonymous, returning the
commit the running instance was built from, read from the platform's environment
(`APP_BUILD_COMMIT`, or Render's injected `RENDER_GIT_COMMIT`, else `"unknown"`):

```csharp
// src/Api/Program.cs — the build-identity probe the smoke polls
app.MapGet("/api/version", () => Results.Ok(new
{
    commit = Environment.GetEnvironmentVariable("APP_BUILD_COMMIT")
             ?? Environment.GetEnvironmentVariable("RENDER_GIT_COMMIT") ?? "unknown",
})).AllowAnonymous();
```

It sits next to `/health` (4.5) but answers a *different* question — not "am I alive?" but "*which
build* am I?" Polling it until it equals `github.sha` is what distinguishes
"my change is live" from "the old build is still answering 200s" — the exact trap §1 opened with.
Health alone can't do this; you need an endpoint that reports *identity*, not just liveness. Once
the right build is confirmed live, a compact assert-block checks the single-origin topology (8.1)
end-to-end against the real URL:

```
assert liveness         200 /health
assert readiness        200 /health/ready
assert build-version    200 /api/version
assert spa-shell        200 /
assert spa-deeplink     200 /settings          # deep link falls back to the WASM shell (8.1)
assert api-not-shadowed 404 /api/does-not-exist # unknown API route is NOT the shell (8.1)
assert providers        200 /api/auth/providers
```

That `spa-deeplink 200` + `api-not-shadowed 404` pair is precisely the 8.1 fallback-routing
correctness, now guarded on *every deploy* — a regression in the fallback order fails the pipeline,
not a user. The smoke is a *post-deploy* gate: it runs against the live environment, after the
deploy, and turns "we think it deployed" into "we verified the new build serves correctly."

## 4. Deploy to prod — the same button, from `main`

```yaml
deploy-prod:
  needs: [build-test, secret-scan, qa-artifacts, license-scan, docker-build, e2e]
  if: github.event_name == 'workflow_dispatch' && inputs.deploy == 'prod'
```

Prod deploys only from a *Run workflow* on `main` with `deploy` = prod, behind every gate, and its own
branch guard refuses anything but `main`. Choosing `prod` **is** the approval: there is no push that can
reach this job. (GitHub can also pause a job on an Environment with a required reviewer, but a private
repo on the free plan has none — and a dispatch already puts a person on the trigger.) This is why
`main` is "deploy-only and behind develop" (the git-workflow rule from the start of the course): work
flows develop → staging → (verified) → main → prod, and every hop to an environment is a deliberate
action. Continuous *delivery*, not blind continuous deployment — the pipeline keeps prod releasable at
any time; a human decides *when*.

## 5. When every minute is billed — a run plan (ADR-031)

On a public repository GitHub's hosted minutes are free; on a private one each is billed against a
monthly allowance, and runner prices differ — macOS bills at 10×, Windows at 2×. Once the native legs
existed (A.1), one push to `develop` cost 57–147 minutes. The platform answers with a CI that spends
minutes only on purpose:

- **A pull request runs the web gates only** — `changes`, `secret-scan` and `qa-artifacts` always (a
  docs-only change can still leak a credential or desync the QA PDFs), and `build-test`, `license-scan`,
  `docker-build`, `e2e` when code changed. A merge runs nothing: its PR already did. No schedule.
- **The device legs run on request** — the MAUI builds, the Release APK and the native smokes run only
  from *Run workflow* → `devices` (android / windows / apple / all). A green PR therefore says nothing
  about the native apps: the maintainer runs them now and then, and before a release.
- **Deploys run on request** — §2 and §4.

One job decides what a run is for, once, and every other job gates on its answer — so no job carries its
own copy of "is this a PR? a deploy? which devices?":

```sh
# .github/workflows/ci.yml — the `changes` job's run plan (excerpt)
checks=false; web=false
if [ "$EVENT" = "pull_request" ]; then
  checks=true; web="$CODE"
elif [ -n "$DEPLOY" ] && [ "$DEPLOY" != "none" ]; then
  checks=true; web=true   # a deploy runs every web gate first, whatever the diff
fi
```

The jobs read it as `if: needs.changes.outputs.web == 'true'`, `…checks…`, or a device output
(`android` / `windows` / `apple`, and a `buildmatrix` the native build expands with `fromJSON`). The
plan's shell runs for real against fixtures in `tests/ci-logic/` (a PR never runs devices; a deploy runs
every web gate; android-only runs android only), and `CiWorkflowTests` holds the shape statically — no
push or schedule trigger, every job in exactly one group, deploys dispatch-only behind every web gate,
a timeout on every job (GitHub's default is six hours: one hung job would eat the month).

Two smaller choices follow the same logic. E2E runs as **one shard**: three shards finished sooner, but
each booted the whole stack again, and on billed runners the repeated setup cost more than the
wall-clock it saved. And the NuGet cache is keyed on the committed lockfiles.

*History:* from 2026-09-16 to 2026-10-02 the platform ran this pipeline on a self-hosted Forgejo, with a
second copy of the workflow held to the first by a parity test (ADR-028). It was retired when the forge
moved back to GitHub (ADR-030), and the lesson it left is the one this section uses: decide *on purpose*
what each run is for.

## 6. Release readiness — the QA plan is an artifact

Automation gates *regressions*; a human QA pass gates *releases*. The platform ships
`docs/QA_TEST_PLAN.md` — a maintained checklist of **173 cases** spanning web plus all four native
platforms (Windows/Android/iOS/macOS): smoke tests, regression tests, and a §13 native release
checklist. It's a *versioned artifact*, edited alongside the code (a new feature adds its QA cases),
with generated PDF run-logs a tester fills in (the course's tooling regenerates them from the
Markdown). Treating manual QA as an *artifact* — not an ad-hoc "click around before shipping" — is
the lesson: it makes release readiness repeatable and reviewable, and it honestly scopes what
automation covers versus what a person must verify (real-device OAuth, email rendering, native
window behavior, visual correctness). The two halves compose: CI's automated gates keep `develop`
continuously releasable; the QA pass is the deliberate human sign-off before a prod release.

## 7. Red — the pipeline gates, exercised

The pipeline itself is the test, but its behaviors are observable and were verified:

```gherkin
Scenario: staging deploys only when the full bar is green
  Given a deploy run (deploy = staging) whose build has a failing test
  Then deploy-staging never runs (needs: build-test failed)

Scenario: the smoke waits for the new build, not the old one
  Given a deploy in progress (old build still serving 200s)
  Then the smoke keeps polling /api/version until it equals the run's SHA before asserting

Scenario: back-to-back deploy runs don't fail each other
  Given two deploy runs seconds apart
  Then the older deploy job is cancelled (neutral), the newer runs its full smoke

Scenario: a deploy from the wrong branch fails loudly
  Given a Run workflow on main with deploy = staging
  Then the web gates run and deploy-staging fails at "staging deploys from develop"

Scenario: nothing deploys, and no device leg runs, on a pull request or a merge (ADR-031)
  Given a pull request into develop that changes src/Shared.Ui
  Then only the web gates run
  When it is merged
  Then nothing runs

Scenario: the device legs run when asked for, and only those
  Given a Run workflow with deploy = none and devices = android
  Then the Android build, the Release APK and the Android smoke run, and no web gate does
```

The version-gated-smoke scenario is the one that captures the lesson's core insight; it's what
makes the pipeline honest about "live" versus "deployed." The last three are what `CiWorkflowTests`
and the run plan's fixtures assert — the triggers, the branch guards, which jobs a run plan selects —
rather than by driving a real deploy.

## 8. Run it

```sh
# open a pull request → only the web gates run (a docs-only PR: changes, secret-scan, qa-artifacts).
# Actions → CI → Run workflow on develop → deploy = staging: the web gates re-run, then deploy-staging
#   triggers Render, polls /api/version until your commit is live, and asserts the smoke block.
# Run workflow on main → deploy = prod: the same, against prod.
# Run workflow → devices = android | windows | apple | all: only those native legs run.
# regenerate the QA run-log PDFs from docs/QA_TEST_PLAN.md, then run the smoke checklist by hand.
```

## 9. Architecture Decision

> **The fork:** how does code reach production, and how is a release judged ready? (a) Manual
> deploys (someone runs a script / clicks the dashboard); (b) fully automatic deploy to prod on
> every green merge, health-check only; (c) auto-to-staging with a *version-gated* post-deploy
> smoke, gated-to-prod behind a human approval, plus a maintained QA plan for what automation can't
> cover.
>
> **Chosen:** (c) (ADR-017, DEPLOY-3). Auto-to-staging keeps `develop` continuously verified against
> the real environment; the version-gated smoke proves the *right build* is live (not the old one
> still serving); the prod environment-approval keeps releases deliberate; deploy concurrency stops
> back-to-back merges from failing spuriously; and the QA plan honestly scopes and gates the
> human-only checks. Automation catches regressions fast; a person signs off releases.
>
> **Rejected:** (a) — manual deploys are error-prone, unaudited, and bus-factor-one. (b) — fully
> automatic prod-on-merge with only a health check ships the "old build still 200s" lie and removes
> the human judgment that catches what tests don't; too much blast radius for this app's stage.
>
> **The trade:** a human approval on prod adds latency to releasing (intentional — that's the
> deliberation), and a maintained QA plan is real ongoing work (~173 cases to keep current). Accepted:
> the latency is the safety, and a versioned QA artifact is how release readiness stays repeatable
> instead of vibes. The version-gated smoke costs several minutes of polling on the free tier — a
> fair price for never mistaking a stale instance for a live deploy.
>
> **Amended (ADR-028, 2026-09-16 + addenda):** when the platform moved to a self-hosted Forgejo as
> `origin`, "auto-to-staging" gave way to *deploy as a dispatch*: pushes run every gate and deploy
> nothing; a person picks `deploy=staging`/`prod` (or `deploy.yml` for an already-green commit), and
> the deploy publishes by a fast-forward-only push to the GitHub mirror that Render follows. Rejected
> there: one forge-aware `ci.yml` (conditions threaded through the file GitHub runs today, for every
> future reader) and image-backed Render services (a registry, new services, and losing "redeploy
> from GitHub"). The version-gated smoke, the prod gate's intent and the QA plan are unchanged —
> only *who* pulls the trigger moved.
>
> **Amended (ADR-031, 2026-10-02):** back on GitHub alone, with every minute billed, the dispatch
> stayed and the rest followed it: pull requests run the web gates only, a merge runs nothing, deploys
> run every gate in their own run, and the native legs run on request. The prod reviewer gave way to
> the dispatch itself (no Environment reviewers on a private free repo). The Forgejo copy, its parity
> test, the mirror push and the already-green deploy were retired with the forge.
