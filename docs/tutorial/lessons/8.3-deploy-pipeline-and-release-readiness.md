# Lesson 8.3 — The deploy pipeline & release readiness

> **Part 8 · Ship it.** The DevOps thread that started in lesson 1.6 — a CI workflow born at the
> first commit and grown a job per part — reaches its destination here: it learns to *deploy*.
> On the hosted pipeline you write first, a push to `develop` deploys to staging and then **proves
> the new build is actually live** before calling it green; prod deploys only behind a human
> approval. Then §5 takes the *decision* to deploy off the merge entirely: on the platform's own
> forge (ADR-028) nothing deploys on a push — a person picks `deploy=staging` on a green commit,
> and GitHub becomes the mirror the host follows. But automation is only half of release
> readiness. The other half is a **QA test plan**
> — a maintained, human-run checklist across web and the native shells — because some regressions
> (a broken OAuth redirect on a real device, a visual glitch) no automated gate will ever catch.
> The lesson's thesis: *automation gates regressions; the QA pass gates releases.*

**Goal:** a CI pipeline where a staging deploy is immediately followed by a version-gated
post-deploy smoke that waits for *this commit* to be live before asserting; `main`→prod is gated
behind a GitHub Environment approval; concurrent deploys don't spuriously fail each other; the same
pipeline runs as a held copy on a self-hosted forge, where deploys are dispatch-only and publish by
a fast-forward push to the GitHub mirror; and a QA test plan exists as a maintained artifact that
gates releases the automation can't.

**Concepts & principles:** continuous delivery (auto-to-staging, gated-to-prod); the
version-gated smoke (why health alone can't tell old build from new); post-deploy assertions;
environment-approval gates; deploy concurrency (cancel-in-progress); a held workflow copy and the
drift test that holds it; deploy as a human dispatch; fast-forward-only publishing to a mirror;
verifying "already green" against the CI that ran it; regressions-vs-releases (what automation
gates vs what a human QA pass gates); the QA plan as a versioned artifact.

**Maps to:** ADR-017, DEPLOY-3, ADR-028, LOCALCI-4, R80 · repo: `.github/workflows/ci.yml` (the
`deploy-staging` / `deploy-prod` jobs), `.github/scripts/deploy-smoke.sh`, `src/Api/Program.cs`
(`/api/version`), `.forgejo/workflows/ci.yml` (the held copy), `.forgejo/workflows/deploy.yml`,
`.forgejo/scripts/push-to-github.sh`, `tests/Api.Tests/ForgejoCiParityTests.cs` (R80),
`docs/QA_TEST_PLAN.md`.

**Prerequisites:** 1.6 (the CI workflow this extends), 8.1/8.2 (single-origin + the container +
`render.yaml` being deployed), 4.5 (`/health` liveness/readiness — two of the smoke's probes; the
third, `/api/version`, is built in this lesson).

---

## 1. Motivate — "deployed" is not "live", and green tests aren't a release

Two subtle truths shape this lesson. First: triggering a deploy is not the same as the new build
serving traffic. On a rolling host the *old* instance keeps answering while the new one builds and
boots — so if your pipeline triggers a deploy and immediately curls `/health`, it gets a cheerful
200 *from the old build* and reports success before your change is even live. A deploy pipeline
that can't tell "old build still up" from "new build live" is lying to you. Second: a full green CI
run means your *code* is correct against your *tests* — it does not mean the *release* is good. Does
Google sign-in actually complete on a physical Android device? Does the invite email render in a
real inbox? Does the desktop shell's window restore correctly? Automated tests can't economically
cover all of that, and pretending they do is how a "green" release ships a broken OAuth flow. So
the pipeline gets a *version-gated* smoke that proves liveness of the right build, and release
readiness gets a *human* QA pass for what automation can't reach.

## 2. Deploy to staging — on the hosted pipeline, a push to `develop`

```yaml
# .github/workflows/ci.yml — deploy-staging
deploy-staging:
  needs: [build-test, secret-scan, qa-artifacts, license-scan, docker-build, e2e]   # only after all gates green
  if: github.event_name == 'push' && github.ref == 'refs/heads/develop'
  concurrency: { group: deploy-staging, cancel-in-progress: true }
  steps:
    - name: Trigger Render deploy
      run: curl -fsS -X POST "$RENDER_DEPLOY_HOOK_STAGING" > /dev/null
```

The shape: staging deploys **automatically** on every push to `develop`, but *only after* the full
quality bar is green — the `needs:` list gates the deploy behind build/test, secret-scan,
license-scan, the E2E suite, and the docker image build. A deploy is downstream of proof. The
`concurrency` block with `cancel-in-progress: true` handles back-to-back merges: if two pushes land
close together, the older deploy job is *cancelled* rather than left to race — because (§3) the
older run's version-gated smoke could never see its own commit go live once a newer build superseded
it, and would fail spuriously. Cancelling reads as neutral; the newest push still runs its full
smoke. Concurrency control here is a correctness fix, not just tidiness. (This is GitHub's copy of
the workflow, and its push trigger is deliberate: it is the mirror re-deploying whatever the button
in §5 pushes to it. On the platform's own forge the same job waits for a person.)

## 3. The version-gated smoke — prove the *new* build is live

This is the clever, load-bearing part. After triggering the deploy, the pipeline **polls
`/api/version` until it reports *this workflow's commit SHA*** and readiness is 200 — only then does
it run assertions:

```yaml
# wait for the NEW build to actually be live (the old instance serves during the build)
EXPECT=${{ github.sha }}
for i in $(seq 1 50); do
  got=$(curl -s "$BASE/api/version" | jq -r '.commit')
  code=$(curl -s -o /dev/null -w '%{http_code}' "$BASE/health/ready")
  if [ "$got" = "$EXPECT" ] && [ "$code" = "200" ]; then ready=1; break; fi
  sleep 15                                   # free-tier build + cold boot can take minutes
done
[ "$ready" = 1 ] || { echo "::error::new build did not go live in time"; exit 1; }
```

`/api/version` is a small endpoint you add *in this lesson* (DEPLOY-3) — anonymous, returning the
commit the running instance was built from, read from the platform's environment
(`APP_BUILD_COMMIT`, or Render's injected `RENDER_GIT_COMMIT`, else `"unknown"`):

```csharp
// src/Api/Program.cs — the build-identity probe the smoke polls
app.MapGet("/api/version", () => Results.Ok(new
{
    commit = Environment.GetEnvironmentVariable("APP_BUILD_COMMIT")
             ?? Environment.GetEnvironmentVariable("RENDER_GIT_COMMIT") ?? "unknown",
})).AllowAnonymous();
```

It sits next to `/health` (4.5) but answers a *different* question — not "am I alive?" but "*which
build* am I?" Polling it until it equals `github.sha` is what distinguishes
"my change is live" from "the old build is still answering 200s" — the exact trap §1 opened with.
Health alone can't do this; you need an endpoint that reports *identity*, not just liveness. Once
the right build is confirmed live, a compact assert-block checks the single-origin topology (8.1)
end-to-end against the real URL:

```
assert liveness         200 /health
assert readiness        200 /health/ready
assert build-version    200 /api/version
assert spa-shell        200 /
assert spa-deeplink     200 /settings          # deep link falls back to the WASM shell (8.1)
assert api-not-shadowed 404 /api/does-not-exist # unknown API route is NOT the shell (8.1)
assert providers        200 /api/auth/providers
```

That `spa-deeplink 200` + `api-not-shadowed 404` pair is precisely the 8.1 fallback-routing
correctness, now guarded on *every deploy* — a regression in the fallback order fails the pipeline,
not a user. The smoke is a *post-deploy* gate: it runs against the live environment, after the
deploy, and turns "we think it deployed" into "we verified the new build serves correctly."

## 4. Deploy to prod — gated behind a human

```yaml
deploy-prod:
  needs: [build-test, secret-scan, qa-artifacts, license-scan, docker-build, e2e]
  if: github.event_name == 'push' && github.ref == 'refs/heads/main'
  environment: production        # ← the gate: add a required reviewer to this GitHub Environment
```

Prod deploys only on a push to `main`, and the `environment: production` line is the safety gate:
by adding a *required reviewer* to the `production` Environment (repo Settings → Environments), a
prod deploy **pauses for human approval** before it runs. This is why `main` is "deploy-only and
behind develop" (the git-workflow rule from the start of the course): work flows develop → staging
→ (verified) → main → prod, and the last hop is a deliberate, approved action, not an automatic
consequence of a merge. Continuous *delivery*, not blind continuous deployment — the pipeline makes
prod releasable at any time, a human decides *when*.

## 5. The same pipeline on your own forge — ADR-028

Everything above runs on GitHub's hosted runners, and for a course repo that is where you should
stay: the minutes are free enough and the deploy hooks are one secret each. But a pipeline that runs
every push on a third party's machines has two costs that grow with the project — minutes (a
`develop` push with the native legs bills ≈190 minutes, most of it on macOS and Windows runners) and
residence (every branch you ever pushed lives on a server you don't run). When either bites, the
platform's answer (ADR-028, LOCALCI-4) is a self-hosted **Forgejo** on the desk as `origin`, its
runners carrying the hosted labels (`ubuntu-latest`, `windows-latest`) so the *same workflow file*
runs there, and GitHub demoted to a mirror that Render follows. Three mechanisms make that safe
rather than merely possible.

**A held copy, and a test that holds it.** Forgejo reads `.forgejo/workflows/`, GitHub reads
`.github/workflows/`; each forge sees only its own directory. So `ci.yml` exists twice, and a copy
only stays honest if something fails when the two drift. `ForgejoCiParityTests` (rule **R80**) is
that something: it parses both files and asserts the job list, every `runs-on`, every pinned
version and the change classifier agree, naming what drifted —

```csharp
// tests/Api.Tests/ForgejoCiParityTests.cs — the parity test's first fact
string[] forgejoOnly = ["mac"]; // is the MacBook awake? — it is a laptop, not a datacenter VM
Assert.True(github.Keys.ToHashSet().SetEquals(forgejo.Keys.Except(forgejoOnly)),
    "The two CI workflows must define the same jobs — add or remove the job in BOTH files, or "
    + "list a Forgejo-only job in this test with its reason "
    + $"(github-only: [{string.Join(", ", github.Keys.Except(forgejo.Keys))}], "
    + $"forgejo-only: [{string.Join(", ", forgejo.Keys.Except(github.Keys).Except(forgejoOnly))}]).");
```

Every *deliberate* difference is either listed in the test with its reason (the one Forgejo-only
job; the two port-binding jobs — `e2e`, `native-smoke-android` — that go to a one-at-a-time
`ubuntu-host-ports` runner because every job on the WSL runner shares one network namespace) or
marked `LOCALCI-4:` in the copy. The alternative — one forge-aware `ci.yml` threading
`github.server_url` conditions through the file GitHub runs today — was rejected for every future
reader of both. The rule generalises: **when you must duplicate, make the duplicate fail loudly on
drift.** It is 1.6's doc-sync gate and A.1's index.html parity, applied to the pipeline itself.

**Deploys are a button, not a side effect.** Forgejo has no Environments and no required reviewers,
so §4's approval gate does not exist there. The platform replaced it with something stricter for
*both* targets: nothing deploys on a push. The workflow gains two `workflow_dispatch` inputs —

```yaml
# .forgejo/workflows/ci.yml — deploys and native smokes are on demand
workflow_dispatch:
  inputs:
    smokes:
      description: Native smokes to run (the gates and builds always run)
      type: choice
      default: none
      options: [none, windows, android, apple, all]
    deploy:
      description: Deploy after everything is green (staging from develop, prod from main)
      type: choice
      default: none
      options: [none, staging, prod]
```

— and `deploy-staging` fires only for `deploy=staging` dispatched from `develop` (prod: `deploy=prod`
from `main`), still behind every gate and every smoke *selected in that run* (a smoke not selected is
skipped, and a skip is not a failure). Staging no longer tracks `develop` automatically: a person
decides when. Pushes and PRs run the gates, `e2e` and the native *builds* (≈10 min); the native
*smokes* — twenty minutes of emulator and WebView2 on a laptop the maintainer is also working on —
run from the `smokes` input and a Monday schedule.

**Publishing is a fast-forward, never a force.** Render builds from GitHub, never from Forgejo, so a
deploy starts by making the commit exist there, on the branch the service follows.
`push-to-github.sh` does that, and it refuses to rewrite anything:

```sh
# .forgejo/scripts/push-to-github.sh — when GitHub refuses, ask the remote which case this is
if git -c "http.https://github.com/.extraheader=AUTHORIZATION: basic $AUTH" \
     fetch --quiet "https://github.com/$MIRROR_REPO.git" "refs/heads/$BRANCH" 2>/dev/null \
   && ! git merge-base --is-ancestor FETCH_HEAD "$SHA"; then
  echo "::error::GitHub's $BRANCH is not an ancestor of this commit — it has something Forgejo does not. Pull it into Forgejo's $BRANCH (git fetch github && git merge github/$BRANCH), push, and run the deploy again."
else
  echo "::error::GitHub refused the push to $BRANCH and its $BRANCH IS an ancestor of this commit, so it is not a fast-forward problem — read git's message above. A ruleset or a token permission is the usual cause (a commit touching .github/workflows/ needs the mirror token to have Workflows: Read and write, not just Contents)."
fi
exit 1
```

The `merge-base --is-ancestor` check is the whole safety property: if someone merged on GitHub in
the meantime, the mirror holds a commit Forgejo does not, the push is not a fast-forward, and the
deploy *stops and says so* rather than overwriting it. Reconciling is `git fetch github && git merge
github/develop` away — a deploy is also the mirror update, so the two remotes can only diverge on
purpose. Two smaller decisions in the same script: the token travels in a header, never in the URL
(git prints remote URLs in its errors), and the message distinguishes "not a fast-forward" from "a
ruleset refused" — the script fetches the branch to *ask* which case it is, because blaming the
branch for both once sent a reader to merge something already merged. Then the hook fires and the
same `deploy-smoke.sh` from §3 polls `/api/version` until *this* commit is live: the smoke is one
script shared by the GitHub jobs, the Forgejo jobs and `deploy.yml`, so it cannot drift either.
(GitHub's own pipeline runs on that push and re-deploys the same commit — accepted as harmless.)

**A green commit can be deployed without re-running its gates — but only a green one.** The
`deploy` input re-runs the whole pipeline first: right when the commit has not been tested, wasteful
when its merge run went green minutes ago. `.forgejo/workflows/deploy.yml` (ADR-028 addendum,
2026-09-22) is the other half. Dispatch-only, it takes a `target`, requires the branch to match it,
and then asks *this Forgejo's own Actions API* which jobs ran for the checked-out SHA — requiring a
success for `changes`, `build-test`, `secret-scan`, `qa-artifacts`, `license-scan`, `docker-build`,
both `native-build` legs and all three `e2e` shards, counting the matrix legs so a half-run cannot
look green. A missing job, a failure, a docs-only run that skipped the gates, or an API it cannot
reach all refuse and point back to `ci.yml`'s `deploy` input. It does not take anyone's word for "it
was green." The rejected alternative — a `skip_gates` input on `ci.yml` — would thread "was this
skipped?" through every gate's `if:` and every deploy `needs:`, and one careless edit would turn
"everything green" into "nothing ran"; a separate file cannot weaken the existing one.
`ForgejoCiParityTests` pins the guard, the dispatch-only trigger and the shared script.

You do not have to build any of this to finish the course — a learner on GitHub alone has a
complete pipeline after §4. Keep it as the shape to reach for when hosted minutes or third-party
residence start to cost you: a held copy with a drift test, deploy as a human dispatch, publish by
fast-forward only, and never trust "it was green" without asking the CI that ran it.

## 6. Release readiness — the QA plan is an artifact

Automation gates *regressions*; a human QA pass gates *releases*. The platform ships
`docs/QA_TEST_PLAN.md` — a maintained checklist of **156 cases** spanning web plus all four native
platforms (Windows/Android/iOS/macOS): smoke tests, regression tests, and a §13 native release
checklist. It's a *versioned artifact*, edited alongside the code (a new feature adds its QA cases),
with generated PDF run-logs a tester fills in (the course's tooling regenerates them from the
Markdown). Treating manual QA as an *artifact* — not an ad-hoc "click around before shipping" — is
the lesson: it makes release readiness repeatable and reviewable, and it honestly scopes what
automation covers versus what a person must verify (real-device OAuth, email rendering, native
window behavior, visual correctness). The two halves compose: CI's automated gates keep `develop`
continuously releasable; the QA pass is the deliberate human sign-off before a prod release.

## 7. Red — the pipeline gates, exercised

The pipeline itself is the test, but its behaviors are observable and were verified:

```gherkin
Scenario: staging deploys only when the full bar is green
  Given a push to develop with a failing test
  Then deploy-staging never runs (needs: build-test failed)

Scenario: the smoke waits for the new build, not the old one
  Given a deploy in progress (old build still serving 200s)
  Then the smoke keeps polling /api/version until it equals the pushed SHA before asserting

Scenario: back-to-back pushes don't fail each other
  Given two pushes to develop seconds apart
  Then the older deploy job is cancelled (neutral), the newer runs its full smoke

Scenario: prod waits for a human
  Given a push to main
  Then deploy-prod pauses on the production environment until a reviewer approves

Scenario: on the self-hosted forge, nothing deploys on a push (ADR-028)
  Given a push to develop on Forgejo
  Then the gates, e2e and the native builds run, and deploy-staging is skipped
  When a person dispatches ci.yml with deploy=staging
  Then deploy-staging runs behind every gate and every smoke selected in that run

Scenario: the deploy refuses to overwrite the mirror
  Given GitHub's develop holds a commit Forgejo does not
  When the deploy pushes to GitHub
  Then push-to-github.sh stops with "not an ancestor of this commit" and nothing deploys

Scenario: an already-green commit deploys without re-running its gates — only if it was green
  Given deploy.yml dispatched for a commit whose merge run skipped the gates (docs-only)
  Then it refuses and points at ci.yml's deploy input
```

The version-gated-smoke scenario is the one that captures the lesson's core insight; it's what
makes the pipeline honest about "live" versus "deployed." The last three are what
`ForgejoCiParityTests` asserts statically — the dispatch-only trigger, `deploy.yml`'s guard and the
shared script — rather than by driving a real deploy.

## 9. Architecture Decision

> **The fork:** how does code reach production, and how is a release judged ready? (a) Manual
> deploys (someone runs a script / clicks the dashboard); (b) fully automatic deploy to prod on
> every green merge, health-check only; (c) auto-to-staging with a *version-gated* post-deploy
> smoke, gated-to-prod behind a human approval, plus a maintained QA plan for what automation can't
> cover.
>
> **Chosen:** (c) (ADR-017, DEPLOY-3). Auto-to-staging keeps `develop` continuously verified against
> the real environment; the version-gated smoke proves the *right build* is live (not the old one
> still serving); the prod environment-approval keeps releases deliberate; deploy concurrency stops
> back-to-back merges from failing spuriously; and the QA plan honestly scopes and gates the
> human-only checks. Automation catches regressions fast; a person signs off releases.
>
> **Rejected:** (a) — manual deploys are error-prone, unaudited, and bus-factor-one. (b) — fully
> automatic prod-on-merge with only a health check ships the "old build still 200s" lie and removes
> the human judgment that catches what tests don't; too much blast radius for this app's stage.
>
> **The trade:** a human approval on prod adds latency to releasing (intentional — that's the
> deliberation), and a maintained QA plan is real ongoing work (~156 cases to keep current). Accepted:
> the latency is the safety, and a versioned QA artifact is how release readiness stays repeatable
> instead of vibes. The version-gated smoke costs several minutes of polling on the free tier — a
> fair price for never mistaking a stale instance for a live deploy.
>
> **Amended (ADR-028, 2026-09-16 + addenda):** when the platform moved to a self-hosted Forgejo as
> `origin`, "auto-to-staging" gave way to *deploy as a dispatch*: pushes run every gate and deploy
> nothing; a person picks `deploy=staging`/`prod` (or `deploy.yml` for an already-green commit), and
> the deploy publishes by a fast-forward-only push to the GitHub mirror that Render follows. Rejected
> there: one forge-aware `ci.yml` (conditions threaded through the file GitHub runs today, for every
> future reader) and image-backed Render services (a registry, new services, and losing "redeploy
> from GitHub"). The version-gated smoke, the prod gate's intent and the QA plan are unchanged —
> only *who* pulls the trigger moved.
